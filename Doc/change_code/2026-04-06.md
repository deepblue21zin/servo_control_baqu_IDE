## 03:56:45
- 수정 파일:
  - `Core/Inc/can_runtime.h`
  - `Core/Src/can_runtime.c`
  - `Core/Src/app_runtime.c`
  - `Core/Src/stm32f4xx_it.c`
  - `Core/Inc/project_params.h`
  - `Debug/Core/Src/subdir.mk`
  - `Debug/objects.list`
  - `Doc/change_code/2026-04-06.md`
- 무엇을 어떻게 바꿨는지:
  - CubeMX가 생성한 `Core/Inc/can.h`, `Core/Src/can.c`는 CAN1 핸들/MSP 초기화 전용으로 두고, 앱에서 필요한 CAN 명령/상태/큐 로직은 새 파일 `can_runtime.c/h`로 분리했다.
  - `can_runtime.c`는 `hcan1`을 이용해 프로젝트 파라미터 기반 bit timing을 다시 적용하고, filter 설정, polling 기반 RX queue 적재, 표준 ID TX, 상태 출력까지 담당하도록 구성했다.
  - HAL TX mailbox 대기 로직은 `HAL_CAN_AddTxMessage()`가 반환하는 mailbox 비트마스크 형식에 맞춰 다시 정리했다.
  - `app_runtime.c`는 직접 `can.h` 대신 `can_runtime.h`를 보도록 바꾸고, CAN 서비스 루프에서 `CAN_Runtime_Service()`를 먼저 호출한 뒤 누적된 프레임을 처리하도록 정리했다.
  - `stm32f4xx_it.c`에서 CAN 관련 include/IRQ 의존성을 제거해, 나중에 code generation을 다시 해도 인터럽트 파일 충돌 가능성을 낮췄다.
  - 빌드 메타데이터에는 generated `can.c`와 사용자 런타임 `can_runtime.c`가 함께 포함되도록 반영했다.
- 수정 이유:
  - 사용자가 “지금 안 정리하면 나중에 Generate Code 할 때 문제가 더 커질 것 같다”고 지적했고, 실제로 generated `can.c/h`가 생성된 상태라 생성 파일과 사용자 런타임의 역할 분리가 필요해졌다.
  - 이후 CubeMX code generation을 다시 하더라도 생성 파일은 `can.c/h`, 사용자 로직은 `can_runtime.c/h`로 유지되게 만들어 충돌을 줄이기 위함이다.
- 영향 범위:
  - 앞으로 CAN 하드웨어 초기화는 generated `can.c/h`, CAN 명령/상태 처리는 `can_runtime.c/h`가 맡는 구조로 분리되어 유지보수가 쉬워졌다.
  - polling 기반 CAN 수신으로도 현재 벤치 디버깅/명령 수신 요구를 충족하면서, 인터럽트 파일 충돌 위험은 줄었다.
  - `Debug` 빌드가 새 구조에서 다시 통과해 현재 저장소 기준으로 바로 시험 가능한 상태다.
